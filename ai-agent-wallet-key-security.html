Securing wallet keys for onchain AI agents

The threat model is different for agents

A human developer who stores a private key in .env at least controls when that file is read and by whom. An AI agent is different: it processes arbitrary text from external sources, calls tools dynamically, and can be manipulated into surfacing or logging data it was never supposed to touch. The attack surface for credential theft expands at every layer of the stack.

The three places wallet keys most commonly leak in agent systems are the model context window, environment variables that get serialized into logs or tool calls, and MCP servers that handle secrets without isolation. A 2026 study of more than 10,000 MCP servers found credentials leaking in over 10 percent of them. This guide covers how to think about each layer and what patterns actually help.

Never put a private key where the model can see it

The most common mistake is treating key management for agents the same as for a backend service. A backend service reads an environment variable once at startup and uses it in tightly scoped code. An agent can be prompted, via a malicious tool response or injected user message, to repeat, summarize, or log anything in its context. If your private key is in the system prompt, a tool call result, or an environment variable the agent framework serializes into its reasoning trace, it is one prompt injection away from exfiltration.

The bad pattern looks like this:

# Bad: key lives in env, agent reads it directly
import os
from my_agent import run

private_key = os.getenv("WALLET_PRIVATE_KEY")
run(agent_context={"wallet_key": private_key, "task": user_task})

Even if you never log agent_context, many agent frameworks serialize the full context for tracing, retries, or memory. The key is now in your observability stack.

The better pattern keeps the raw key entirely outside the agent:

# Better: agent holds a path reference, not the key
# Signing happens in a separate process that the agent never controls directly
run(agent_context={"wallet_path": "wallets/mainnet/deployer", "task": user_task})

# Signing service, called by a tool, reads the key from a vault
# and returns only the signed transaction hex
def sign_transaction(wallet_path: str, tx: dict) -> str:
    key = vault.get_secret(wallet_path)          # key never returned to agent
    return sign_with_key(key, tx)

The agent only ever sees a path identifier and the signed transaction output. The raw key is handled by a process the model cannot directly introspect.

Key storage: what your options actually are

Hardware Security Modules

An HSM stores private key material in tamper-resistant hardware and exposes a signing interface. The key never leaves the device. Cloud HSMs (AWS CloudHSM, Google Cloud HSM) bring this to managed infrastructure. The tradeoff is cost and operational complexity. HSMs are the right answer when you are managing keys for production systems with real funds at risk.

Cloud KMS with envelope encryption

AWS KMS, GCP KMS, and Azure Key Vault let you store secrets with access policies, audit logs, and key rotation without managing hardware. They are not HSMs in the strict sense, but they provide meaningful isolation from application code. Use IAM roles scoped to the minimum necessary operations, and never grant your agent's runtime identity the ability to export key material, only to call the signing API.

Short-lived credentials

Whatever storage backend you use, the principle is the same: the agent should authenticate with a scoped, short-lived credential, not a long-lived master key. A credential that expires in 15 minutes has a much smaller blast radius than one that never rotates. This applies equally to API keys for external services the agent uses, not just wallet private keys.

Transaction signing without key exposure

For EVM chains, you can structure your signing flow so the agent constructs an unsigned transaction and a separate service handles the signature. The agent calls a tool like request_signature(tx_data, wallet_id) and gets back a signed hex string. It never needs the private key to construct or submit the transaction.

For non-EVM chains the same architecture applies, though the transaction format differs. The key is that the boundary between "agent decides what to sign" and "key material signs it" is a meaningful security boundary. Crossing that boundary should require an explicit, audited action, not just a variable lookup.

Consider also whether your agent should be signing transactions at all without a human approval step for high-value actions. An agent that can unilaterally sign arbitrary transactions is a much larger target than one that queues transactions for human review above a threshold.

Prompt injection and MCP servers

Prompt injection is the scenario where a malicious payload in tool output, a web page, or an external document instructs the model to take unintended actions, including exfiltrating credentials. When your agent calls external tools or reads external data, treat that content as untrusted input, the same way you treat user input in a web application.

MCP servers introduce a specific risk: they often hold credentials to call downstream services, and if those credentials are embedded in the server's environment or returned in tool responses, they can appear in the model's context. The credential leakage rate found in the wild study cited above is high enough that this should be treated as a default-on risk, not an edge case.

At minimum, audit what your MCP servers return in their responses. Credentials should never appear in tool output even as a side effect of normal operation.

A practical checklist

  • Private keys never appear in agent context, system prompts, or tool call parameters.
  • Signing happens in a process the model cannot directly read from or write to.
  • Credentials are short-lived and scoped to the minimum necessary operations.
  • All signing actions are logged with enough context to reconstruct what was authorized and why.
  • Credentials are revocable individually, not tied to a shared master key.
  • Tool and MCP server responses are treated as untrusted input and scanned for injection before reaching the model.
  • High-value transaction signing includes a human approval step or a rate limit.

The core principle is the same one that applies to any privileged credential in a software system: minimize who can see it, minimize how long it is valid, and log every time it is used. The difference with agents is that "who can see it" now includes the model itself, and you have less control over what the model does with what it sees.
