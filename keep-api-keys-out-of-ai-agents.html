How to keep API keys out of your AI agent

When you give an AI agent a real capability, you give it a real credential: an API key, an OAuth token, sometimes a wallet. The way most agents ship, that secret sits in an environment variable and gets read into memory at startup. That was an acceptable pattern for a web server. It is a bad one for an agent, because an agent has far more ways to leak the value than a web server ever did.

Why agents leak secrets that servers do not

A traditional service reads a key, uses it to sign an outbound request, and never exposes it again. An agent is different in three ways that matter:

  • The context window. Agents assemble prompts from many sources, and it is easy for a key in the environment or a config object to get serialized into a prompt, a system message, or a tool description. Everything in that window travels to a third-party inference API and is often retained there.
  • Tool call arguments. When an agent calls a tool, the arguments are model-generated text. A prompt-injected model can be steered into putting a secret it holds into an argument, a log line, or a reply.
  • Logs and traces. Agent frameworks log prompts, completions, and tool I/O by default for debugging. A key that touches any of that is a key in your logs.

A 2026 study of more than 10,000 MCP servers found credentials leaking in over 10 percent of them, largely through tool descriptions and prompt templates that embedded real values. This is not a corner case.

The patterns to stop using

Putting the key in the system prompt

The fastest way to wire an agent to an API is to paste the key into the instructions. Do not. Anything in the prompt is one injection away from being echoed back.

// bad: the key is now in every request to the model
const system = `You are a support agent. Use API key ${process.env.SUPPORT_API_KEY}.`;

Reading raw keys into the agent process

Even if the key never reaches the prompt, holding it in process.env means a compromised dependency, a poisoned tool, or an over-eager code path can read and exfiltrate it. The agent does not need the key. It needs the result of an action that uses the key.

The principle: use a secret without holding it

The durable fix is to make the agent a principal that can use a secret without ever possessing its raw bytes. Three ideas, in increasing strength:

  • Fetch just-in-time, never persist. Pull the secret at the moment of use from a store the model has no path to, use it for one outbound call, and drop it. It never lands in .env or the prompt.
  • Scope and time-box access. Give the agent a short-lived, narrowly scoped token instead of the real key. If it leaks, it expires and only ever reached one path.
  • Keep the secret server-side entirely. Proxy the outbound call through a service that injects the credential, so the agent references a binding, not a value. For signing, sign in an enclave so the private key never leaves it.

Screen untrusted input, too

Keeping keys out of reach handles exfiltration. The other half is not acting on hostile input in the first place. Before your agent acts on a fetched web page, a tool result, or a user message, screen it for injection, PII, and dangerous encodings, and refuse the ones that fail.

Takeaway

Do not ask how to store your agent's API key safely. Ask why the agent holds the raw key at all. Fetch it just-in-time, scope and time-box it, or keep it server-side entirely, and screen what the agent reads. An agent that never possesses a secret cannot leak one.
