Handling secrets safely in an MCP server

Why secrets deserve special attention in MCP servers

Model Context Protocol servers sit at an unusual intersection: they hold credentials needed to call external APIs, and they pass data directly into model context where it can be logged, cached, or echoed in tool results. A secret that leaks into a tool response leaks into the conversation transcript, into any logging layer, and potentially into whatever the model decides to say next. A 2026 study of more than 10,000 MCP servers found credentials appearing in plaintext in over 10 percent of them. The problem is not exotic. It follows from treating MCP servers like ordinary web services, which they are not.

The most common mistakes

Hardcoding credentials in source

The most obvious problem still happens constantly. A developer writes a quick integration, drops the API key in directly, ships it, and forgets.

// Bad: key is committed to version control and visible to anyone who reads the code
const client = new StripeClient({ apiKey: "sk_live_abc123..." });

Beyond the obvious git history risk, any tool that echoes its configuration back as a diagnostic will now surface that key in the model context.

Passing secrets through tool arguments

A subtler pattern: the orchestrating agent is given a secret as a tool argument so it can "pass it through" to a downstream call. Now the secret is in the prompt, in the model context window, and in whatever logs your inference provider keeps.

// Bad: secret travels through model context
{
  "tool": "send_email",
  "arguments": {
    "smtp_password": "hunter2",
    "to": "user@example.com"
  }
}

A prompt injection in any prior tool result could exfiltrate that secret by inducing the model to repeat it back in a subsequent call.

Logging full request bodies

MCP servers often log for debugging. If you log the full incoming JSON or the full outgoing HTTP request, you may be logging secrets sitting in headers or request bodies. Structured loggers that redact known fields help, but field names are not consistent across APIs.

Better patterns

Use environment variables, loaded once at startup

Environment variables are not perfect, but they keep secrets out of source control and out of tool argument flows. Load them at process startup, store them in a module-scoped variable, and never pass them as arguments through tool calls.

// Better: loaded at startup, never passed through model context
const STRIPE_KEY = process.env.STRIPE_SECRET_KEY;
if (!STRIPE_KEY) throw new Error("STRIPE_SECRET_KEY is required");

// The tool implementation uses the module-scoped variable directly
async function chargeCard(amount: number, token: string) {
  const client = new StripeClient({ apiKey: STRIPE_KEY });
  return client.charges.create({ amount, source: token });
}

The model never sees STRIPE_KEY. It calls charge_card with business arguments, and the server resolves the credential internally.

Scope credentials to the minimum required

Most APIs offer scoped tokens. A key that can only read does not help an attacker who wants to write. A key scoped to one resource cannot be used against another. Request the narrowest token your tool actually needs. Rotate keys on a schedule and after any suspected exposure.

Redact secrets from all log output

Assume logs will be read by people and by tools. Before writing any log line that includes an HTTP request or response, strip known-sensitive headers like Authorization, X-API-Key, and Cookie. For request bodies, either log only a subset of fields or use a structured redaction library. Do not log full tool inputs and outputs in production.

function redactHeaders(headers: Record) {
  const sensitive = new Set(["authorization", "x-api-key", "cookie"]);
  return Object.fromEntries(
    Object.entries(headers).map(([k, v]) =>
      sensitive.has(k.toLowerCase()) ? [k, "[REDACTED]"] : [k, v]
    )
  );
}

Validate tool inputs to reduce injection surface

Prompt injection can cause a model to pass unexpected values into tool arguments. If your tool accepts a file path, validate that it stays within an allowed directory. If it accepts a URL, check the scheme and host. If it accepts free text that gets interpolated into a shell command, either avoid that pattern entirely or sanitize with strict allowlisting. The narrower the accepted input, the smaller the footprint for an attacker who has injected into the conversation.

Isolate the MCP server process

An MCP server that can read arbitrary environment variables is a larger target than one that loads only what it declares. Use a dedicated process user with minimal filesystem permissions. If you run in a container, do not mount the host environment or the host filesystem. Secrets managers like AWS Secrets Manager, HashiCorp Vault, or GCP Secret Manager can inject secrets at runtime into a scoped process without putting them in environment files that might be checked in or copied.

A practical checklist

  • No credentials in source files or committed configuration.
  • Secrets loaded once at startup from environment variables or a secrets manager, never passed as tool arguments.
  • Log redaction applied to all HTTP headers and any request body fields that might carry credentials.
  • Tool inputs validated and constrained to prevent injection from escalating to credential exfiltration.
  • API keys scoped to the minimum permissions required by the tool.
  • Key rotation on a schedule, with a documented revocation procedure for suspected exposure.
  • MCP server process isolated with a dedicated user and no unnecessary filesystem or environment access.

The goal is that a complete transcript of every conversation your MCP server participates in, including all tool inputs and outputs, should contain no information that would help an attacker. Treat the model context as a public channel and design accordingly.
