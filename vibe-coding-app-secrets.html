Vibe-coded your app? Here is how to stop it leaking its secrets

The problem with vibe-coded apps and secrets

AI coding tools like Cursor, Bolt, Lovable, and Replit are genuinely good at getting an app running in an afternoon. The catch is that the same prompts that generate working code also tend to generate credentials baked directly into source files. That code lands in a git repository, the repository gets pushed to GitHub, and GitHub is public by default. Automated bots scan public repositories for credentials around the clock, and a leaked API key can be abused within minutes of appearing online.

A 2026 analysis of over 10,000 MCP servers found credentials leaking in more than 10 percent of them. Those were not all careless beginners. The pattern shows up everywhere when developer tooling handles secrets implicitly rather than explicitly.

This guide shows you the concrete steps to keep secrets out of your source code, your git history, and your logs.

Where secrets leak: the most common patterns

Hard-coded values in source files

The most direct form. An AI tool generates a working example and puts the key right in the code:

// bad: never do this
const stripe = new Stripe("sk_live_4xR9...");
const db = mysql.createConnection("mysql://admin:hunter2@prod.db.example.com/app");

This is bad because the secret is now in plain text in every clone, fork, and CI log that touches the file. Read the environment instead:

// better
const stripe = new Stripe(process.env.STRIPE_SECRET_KEY);
const db = mysql.createConnection(process.env.DATABASE_URL);

Secrets in frontend code

Any value your build tool bundles into client-side JavaScript is visible to anyone who opens the browser developer tools. There is no such thing as a secret that lives in a React component or a Svelte store. If a key authorizes a privileged API call, that call must happen on a server you control, not in the browser.

The one exception is a key that is intentionally public-facing and carries no privileges, such as a Stripe publishable key or a maps embed key that is restricted by HTTP referrer. Even those should be in environment variables so you can rotate them without a code change.

The right foundation: .env files and .gitignore

Create a .env file at the root of your project for local development secrets. Most frameworks (Next.js, Vite, SvelteKit, Express) load this file automatically, or you can use the dotenv package.

OPENAI_API_KEY=sk-proj-...
STRIPE_SECRET_KEY=sk_live_...
DATABASE_URL=postgres://user:pass@localhost/myapp

Then immediately add .env to your .gitignore. Also add any variant names your tools might create:

.env
.env.local
.env.development.local
.env.production.local
.env.*.local

Commit a .env.example file that shows the variable names but not the values. This lets teammates and deployment tools know what is needed without exposing anything real:

OPENAI_API_KEY=
STRIPE_SECRET_KEY=
DATABASE_URL=

Dealing with secrets already in git history

If a secret was committed even once, assume it is compromised. Removing it from the current HEAD does not remove it from git history. The correct response is to rotate the secret immediately, which means generating a new key and revoking the old one at the provider. Do this before spending time on cleanup.

After rotating, you can remove the secret from history using git filter-repo or BFG Repo Cleaner, but this rewrites history and requires force-pushing, which causes problems for anyone who has cloned the repository. For most vibe-coded projects the pragmatic path is: rotate the key, make the repo private, and ensure your current code reads from environment variables.

Scanning before you push

Git hooks let you catch leaks before they leave your machine. git-secrets and gitleaks are both free tools that scan staged files for credential patterns:

# install gitleaks (macOS)
brew install gitleaks

# scan the current repository
gitleaks detect --source .

GitHub itself runs secret scanning on public repositories and will notify you if it finds a credential from a supported provider. You can also enable push protection to block the push entirely.

Secrets in production and deployment platforms

Never put secrets in deployment configuration files that are checked into git, such as docker-compose.yml, vercel.json, or fly.toml. Use the environment variable management built into your platform instead.

  • Vercel, Netlify, Railway, Render: each has a dedicated environment variables UI in the dashboard and a CLI command to set them.
  • Replit: use the Secrets tab in the sidebar, not the editor.
  • Docker: pass secrets with --env-file at runtime or use Docker secrets for swarm deployments.

Environment variables set through a platform UI are injected at runtime and are not stored in your repository or visible in build logs.

Principle of least privilege

Every API key should do exactly one job. A key that only reads from a database should not have write permissions. A key that sends emails should not have access to billing. Most providers let you create scoped keys with specific permissions. Use them. When a key leaks, the blast radius is then limited to what that key could actually do.

The short checklist

  • No secrets in source files. Read from environment variables.
  • .env is in .gitignore before the first commit.
  • Commit a .env.example with empty values.
  • No secrets in frontend JavaScript. Put privileged calls on a server.
  • Use scoped keys with minimum necessary permissions.
  • Rotate any key that was ever committed, immediately.
  • Set production secrets through your deployment platform's UI, not in config files.

These habits cost very little time to build and save a significant amount of pain. The AI tools that generated your app can also help you find and fix leaked secrets if you ask them to audit your codebase for hard-coded credentials as a separate pass.
